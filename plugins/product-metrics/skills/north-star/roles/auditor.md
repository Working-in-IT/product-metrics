# Auditor — оценка кандидата

Возьми из запроса режим, определение метрики, пользователя и его полезный результат. Четыре критерия для быстрой оценки выбраны в роли Auditor проекта AI Analyst Lab (ссылка в конце). Смысл семи критериев задан в [чек-листе Amplitude](https://amplitude.com/books/north-star/the-north-star-checklist).

## Быстрая оценка (`triage`)

Проверь по порядку четыре вещи: получает ли пользователь ценность, предшествует ли событие бизнес-результату, есть ли у команды действие для влияния на показатель, можно ли увеличить число без дополнительной пользы.

- Если есть конкретный контрпример, который опровергает один из этих критериев для данного определения, остановись на нём и передай его [Refuser](refuser.md).
- Если хотя бы один ответ неизвестен или противоречив, предложи полный аудит и назови одну проверку, которая больше всего изменит решение.
- Если по всем четырём есть основания, скажи, что кандидат прошёл предварительную проверку. Для выбора метрики команда ещё должна оценить стратегию, понятность и измеримость.

Верни вердикт, главное основание и следующий шаг в нескольких строках.

## Полный аудит (`audit`)

Верни по строке на критерий. Различай подтверждение, слабое основание, установленное противоречие и отсутствие данных. Укажи наблюдение из продукта или способ его получить. Для слабого места предложи конкретную правку определения или проверку.

| Критерий | Что установить на примере продукта |
|---|---|
| Польза | Какой результат человек получил к моменту учтённого события? |
| Стратегия | Как показатель различает успех и неудачу выбранной стратегии? |
| Опережающий сигнал | Какой более поздний бизнес-результат он помогает предсказать? Укажи лаг, когорту и проверку на истории. |
| Возможность влиять | Какое решение команды способно изменить один из входов? |
| Понятность | Сможет ли коллега по примеру сказать, какой случай попадёт в расчёт? |
| Измеримость | Заданы ли событие, единица, период и способ воспроизвести число? |
| Риск формального роста | При каком действии число вырастет, а пользовательский результат останется прежним или ухудшится? |

В итоговом вердикте установленный провал одного из четырёх критериев быстрой оценки означает «кандидата стоит заменить или переопределить». Используй [Refuser](refuser.md) для обоснования после таблицы. Для пробелов или оставшихся слабых критериев верни «требует проверки». Согласованный и проверенный косвенный показатель допустим при известной связи с результатом. Отдельно укажи свидетельства о продукте и ссылку на методику.

Например, для учебного Beacon «MAU по входу в приложение» вырастет, если обязать прежних анонимных читателей справки войти в приложение, даже когда их задачи и результат те же. Уточни, сколько людей завершили полезный сценарий. Кандидат «пользователи с успешным сценарием за месяц» всё ещё требует проверки связи с последующим удержанием.
