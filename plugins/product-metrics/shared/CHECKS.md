# Проверка каталога

Проверяйте эти условия при записи и перед передачей комплекта. Это процедура содержательной проверки; автоматического валидатора карточек в первой версии нет.

## Структура и ссылки

Откройте профиль, затем реестр и каждую изменённую карточку. Проверьте обязательные поля и типы, допустимые статусы, совпадение префикса ключа с продуктом, уникальность ключей и соответствие строки реестра шапке. Проверьте наличие всех актуальных карточек в реестре и отсутствие в нём исторических копий. Все локальные ссылки должны открываться относительно файла, в котором стоят.

Для системы проверьте существование ключей и совпадение версий, уникальность целей и участников внутри цели, направления связей и отсутствие циклов расчёта. Ссылки `evidence` должны подтверждать именно заявленный статус, а не просто вести на страницу.

## Содержательные сценарии

Учебный каталог позволяет проверить поведение на конкретных неоднозначностях.

| Запрос | Ожидаемый результат |
|---|---|
| «Найди MAU» | Два кандидата: Atlas за календарный месяц и Beacon за 30 суток; выбор без продукта неоднозначен |
| «Почему MAU нельзя сложить по дням?» | Повторные пользователи считаются один раз за всё окно; нужно объединение идентификаторов |
| «Как считается success rate Beacon?» | Успешные / все допустимые сценарии одной зрелой когорты; нулевой знаменатель даёт `null` |
| «Снизилось среднее время: стало лучше?» | Проверить долю успеха, объём и состав сценариев; по одному среднему вывода нет |
| «Уберём отменённые сценарии из знаменателя» | Изменение определения: новая версия и решение о сопоставимости, а не редакционная правка |
| «Карточка agreed, данные проверены?» | Статус согласования не доказывает проверку реализации; прочитать свидетельства |
| «Более быстрый сценарий повышает аудиторию?» | В примере это `hypothesized_driver` со статусом `untested`, не доказанный эффект |

Для запроса об изменении знаменателя выполните пробную правку в отдельной копии: сохраните прежнюю полную версию, оставьте старым замерам прежний номер, обновите реестр и выявите потребителей, использующих старую версию. Если нет подтверждения принятия методики, сохраните предложение отдельно.

## Сценарии новых режимов

Данные - учебные продукты Shop и Platform, Beacon и ряды из [examples/data](examples/data/). Скиллы: `diagnose-metric`, `metrics-memo`, `metrics-system` (режимы `map`, `experiment`, `okr`), `metrics-review` (режимы `dashboard`, `vanity`).

| Запрос | Ожидаемый результат |
|---|---|
| «Средний чек упал с 67,9 до 61,7, почему?» (окна по 1000 заказов; Premium 700 по 85 -> 550 по 86, Standard 300 по 28 -> 450 по 32) | Вклады замыкаются: состав -8,55, средние +2,35, сумма -6,2; названы порядок разложения и уровень «локализовано»; причина сдвига состава не установлена; заказов поровну, выручка ниже на 6 200 - не потерянная прибыль |
| «Из чего состоит WAU 5 на неделе t?» (прошлая неделя 4 пользователя) | Три непересекающиеся части: удержанные 2, новые 2, вернувшиеся 1; сумма 5; ушедшие (2) - мост между неделями, не слагаемое; это формула, не причина |
| «Поставим KR на рост WAU» | Не принимать цель на корне: показать, что без действий WAU идёт к равновесию 6; предложить KR на удержанных; базу, цель, срок и владельца, которых нет, оставить в `[...]` и назвать цель предложением |
| «Запускаем тест напоминаний, какие метрики брать» | Success, guardrail и допуск названы до запуска; допуск без основания - «неизвестно»; напоминание остаётся гипотезой `untested`; дизайн и горизонт записаны до результата |
| «Beacon: время 50 -> 30 минут, значит лучше?» | Одной метрики мало: guardrail - доля успеха (80% -> 60%); допустимое падение не задано, проверку безопасной не называть; среднее считается по выжившим |
| «Недельный средний чек: 8 недель, максимум 68,6 на неделе 5 - объясни, почему она лучшая» | Пределы 65,96 ... 69,99 предварительные (8 точек); 68,6 внутри - не объяснять, строку в записке оставить; значение 61,7 ниже нижнего предела - исключение с владельцем и вопросом, причина не установлена |
| «Ревью дашборда Beacon: карточка "Время" зелёная, "Успех" 46,7%» | Блокирующие замечания: время без доли успеха; общая доля - среднее процентов сегментов (верно 600/1000 = 60%); качество результата не определено, порога нет; вердикт «не готов к решению» |
| «Это vanity-метрика?» без отчёта и решения | Сначала контекст или условные вердикты; без решения, управляемости и связи с ценностью вердикта нет; расчёт не считать проверенным по описанию |
| «Метрика упала» при пустом каталоге | Ответ по методологии без записи файлов; неизвестные база и версия названы; в конце одна строка с предложением сохранить записку |

Во всех сценариях значение, которого нет в запросе, остаётся неизвестным: версия определения, база, порог, владелец и срок не придумываются.

## Воспроизведение расчёта

По [правилам расчёта](references/CALCULATION.md) проверьте, что из карточки доступны полный код, движок, входы, параметры, результат и состояние проверки. Сопоставьте SQL с единицей наблюдения, фильтрами, окном, числителем, знаменателем и агрегацией. Отдельно проверьте подготовку данных и преобразования после запроса.

- «Добавь готовый SQL к прежнему определению» - сохранить условия запуска и версию кода; без изменения смысла номер определения остаётся прежним.
- «SQL проверен на нескольких строках, значит вся метрика проверена?» - нет, свидетельство относится только к указанным данным и шагам.
- «В старом запросе ошибка; сохрани исправление» - различить исправление реализации и изменение самой методики, сохранить старый код для прошлых замеров.
- «Как посчитать без доступа к схеме?» - показать известную процедуру и пробелы; учебные таблицы не выдавать за реальные.

Запустите [учебные SQL-проверки](examples/sql/README.md) в отдельной локальной базе. Они проверяют арифметику и границы двух запросов; не проверяют подготовку событий или данные организации.

## Передача

Распакуйте подготовленный архив в пустую папку вне рабочего каталога. Повторите проверку ссылок и сценарии поиска только по его файлам. В комплекте общего назначения не должно быть локальных абсолютных путей, закрытых корпоративных адресов, данных организации или ссылок на отсутствующие внешние локальные файлы. Служебные манифесты в скрытых папках включаются явно; личные настройки и история исходного рабочего репозитория не включаются. Сверьте перечень файлов и их содержимое с подготовленной исходной папкой.

Такая проверка доказывает целостность документов и примеров. Удобство для незнакомого пользователя и качество будущих ответов агента требуют отдельного пилота на реальных задачах.
